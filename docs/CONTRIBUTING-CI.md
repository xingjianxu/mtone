# 按改动验证，合并后发布文档

普通组件、代码和文档改动只跑相关检查。得到合并授权后，先验证拟合并结果，再推进 `master`。Pages 只核对验证凭据并构建部署，不重跑测试。稳定 npm 发布只做[版本与安装包检查](RELEASING.md)；全量单元与浏览器回归仅在明确要求时手动运行。

## 普通修改跑什么

候选从实际的两次 Git 提交差异计算范围，重命名的旧、新路径都会考虑。可以先审阅计划：

```sh
node scripts/check-targeted-changes.mjs <远端-master-SHA> <候选-SHA> --plan
```

- 纯 Markdown、授权说明和许可证改动：核对 checkout 与跟踪文件一致性，不安装依赖，不跑组件或浏览器测试。生成参考所需输入不变；Pages 构建仍检查网站与参考文件。
- 文档应用和示例：文档构建、生成参考核对、文档相关测试；入口、搜索、布局等改动加对应视觉/交互检查。组件文档可以只有父页面中的章节，不要求另建独立页；测试验证导航实际使用的页面与锚点。
- 组件源码、样式、测试和夹具：按组件家族及显式依赖选择测试。例如侧栏导航与 NavSubmenu 关联，DataTable 的筛选和模型关联 DataTable。合并同一候选涉及多个组件时会合并测试清单，重复条目只执行一次。
- 公共入口、全局样式、锁文件、跨组件依赖或未映射路径：有限的代表性冒烟检查，并记录未映射路径，不静默跳过，也不默认跑全量。新增接口或共享模块时，应把关联测试加入范围清单。工作流/验证脚本改动跑专门的 CI/发布单测。
- 只运行相关浏览器脚本。已有脚本若内部覆盖三浏览器，保留其覆盖；可选引擎的脚本在普通候选选 Chromium。保留旧版组件工作流入口，但它们也只跑本组件或已明确关联组件的检查。

## 授权后合并

先整合当前远端 `master` 与待合并改动，审阅最终提交并保持工作树干净。需要向 `github.com/xingjianxu/mtone` 推送的 Git 凭据，以及 GitHub CLI 的读取权限。

```sh
node scripts/merge-verified.mjs --expect-master <已核对的远端-master-SHA> [候选]
```

候选可传本地提交 SHA 或引用；缺省为 `HEAD`。入口创建或复用同仓库 `release-candidate/<master基线SHA>/<候选SHA>`。GitHub 检出事件指定提交，并确认分支编码的基线仍等于远端 `master`，之后按差异执行 **Targeted validation**。运行最多等待约一小时；已有精确同一候选的验证时，重试不会重新推送和重复测试。脚本要求成功的实际验证作业、对应尝试及检查步骤，并核对候选树。超时、失败、分支变化或证据缺失时不会推进 `master`。

验证成功后，入口再次核对远端基线及候选，用带旧值检查的普通 Git 快进推送，不强推、不覆盖并发更新，并保留可执行的本地 `pre-push`。结束输出精确提交的 Pages 追踪线索，不代表发布已完成。若 master 已等于候选，只输出追踪，不做写入。

若 `master` 受保护，使用相同验证过的候选走获授权的 PR 合并路径。最终完整 Git 树和当前 master 基线都必须不变；merge、squash 或 rebase 产生的新 SHA 可以接受，但冲突解法、目标分支或候选变化时须生成新候选。GitHub 内置 `GITHUB_TOKEN` 执行推送可能不产生运行；先确认准确分支和提交，再在 Documentation 对候选分支手动运行一次。不要启动重复运行。

## Pages 与重试

正常推送从 GitHub 事件取合并前的 `master` 基线，并与候选的基线和完整 Git 树匹配。使用同仓库 Documentation 的已完成成功 **Targeted validation**，而不是只看工作流总状态。通过后只构建该事件提交，并上传本次构建产物，不下载候选产物或重复跑测试。部署前确认目标仍是当前 `master`；部署成功后核对线上 `llms.txt` 与目标提交。

需要重试时，在 Actions 里重跑**原先相同 SHA 对应的 `master` 推送运行**（也可用 `gh run rerun <run-id>`）；新建手动运行不会发布 Pages，因此无法以别的基线替代原推送的 `before`。如果从未产生原始推送运行，不要补填任意基线或手动上传；先核实触发权限和记录，确有必要则由获授权的整合者基于当前 `master` 验证并推进新的候选。首次启用时，新策略候选本身应包含新版工作流，并在推进 `master` 前先获得这个候选的验证结果。旧版作业不替代新版有基线绑定的验证。

## 权限边界

合并入口先验证再推送；Pages 门禁本身不拦截其他写入者直接改 `master`，也不是仓库级分支保护。只有获授权、受信任的整合者可以把已看过的变更放入同仓库候选；要在仓库层强制规则，应由管理员另行配置。候选只使用读取权限，不注入仓库秘密；只有现有的 `github-pages` 作业获得 Pages/OIDC 权限。合并与文档发布不等于授权发布 npm。
